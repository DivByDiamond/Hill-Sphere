# Hill Sphere — дизайн

Рабочий документ. Числа ниже — стартовые значения для прототипа, они пойдут в конфиг и
будут подбираться на игре. Названия блоков и ID специально не зафиксированы: ID,
записанный в сохранение, потом не поменять. Что решено, а что нет, видно в разделе
«Решения и открытые вопросы».

## Идея

В ваниле «вниз» один и тот же везде. Мод даёт построить свой «низ»: ставишь блок-ядро,
раскручиваешь его вращением Create, и вокруг него появляется область, где «вниз» смотрит
на ядро (или от него). Не планета, не измерение, не генерация рельефа — блок и поле вокруг.

Название: *hill sphere* — область, где притяжение данного тела пересиливает остальные
рядом. Правило выбора поля (ниже) сделано именно так, поэтому название честное.

Что это даёт в игре:

- построить станцию на своём «шарике» и не падать с неё
- перевернуть пол: ходить по потолку корабля, пока рядом работает ядро
- садиться кораблём на свою маленькую планету как на манёвр (после интеграции с Sable)
- увидеть поле глазами: гравитационные очки показывают границы и направление

Чего в моде нет:

- генерации рельефа и измерений. Единственное исключение — жила руды (см. вопросы)
- своей физики твёрдых тел: корабли считаются в Sable
- энергии «из воздуха»: поле стоит вращения, и сеть Create должна его тянуть

## Блоки и предметы

| Сущность | Роль |
|----------|------|
| Руда (`gravite`) | единственный сырьевой ресурс мода, копается в мире |
| Ядро поля (`hill_core`) | кинетический блок: потребляет вращение, создаёт поле |
| Плита | обшивка вокруг ядра: из точки делает «тело», по которому можно ходить |
| Гравитационные очки | предмет в слот головы, показывают поля (см. «Очки») |
| Гироскоп | локально гасит вращение/увод, чтобы корабли не крутило (поздно) |

Отдельного блока-отталкивателя нет: притяжение/отталкивание — настройка самого ядра.
Отдельного «грузила» тоже нет: направление «низа» в точке показывают очки.

Ядро — единственное, что создаёт поле. Плита и гироскоп поле только читают или
модифицируют.

## Ядро поля

Ядро — кинетический потребитель Create. Источник энергии — вращение, как у любой машины:
скорость (RPM) приходит по валу, нагрузка на сеть измеряется в SU (stress units).

### Что от чего зависит

| Параметр поля | От чего зависит |
|---------------|-----------------|
| Радиус | скорости вращения |
| Сила | выбранным уровнем силы (то есть тем, сколько вращающего момента ядро берёт) |
| Знак (притяжение / отталкивание) | настройкой на грани |
| Включено ли поле | редстоуном и тем, что сеть не перегружена |

Стартовые формулы (все константы — в конфиг):

```
скорость     v = |RPM|                      (направление вращения не важно)
радиус       R = R_min + (R_max − R_min) · min(v, 256) / 256        R_min=2, R_max=32 блока
минимум      v < 8 RPM → поле выключено
уровень      L ∈ {1, 2, 3, 4}               настраивается игроком
сила         g = g_L                        g_1=0.25, g_2=0.5, g_3=1.0, g_4=1.5  (в долях ванильной g)
нагрузка     S = v · k · L                  k = 4 SU на RPM на уровень
```

Смысл: радиус — это «как быстро раскручено», сила — «сколько момента взято». Ядро на
256 RPM и уровне 4 стоит ~4096 SU (много: несколько крупных источников); на 64 RPM и
уровне 1 — 256 SU (дёшево, но радиус около 9 блоков и слабое поле). Маленький шар с
ванильной силой тяжести дёшев, огромный и сильный — дорог. Это и есть торговля
«вращающий момент против размера поля».

Нагрузка ядра считается как у остальных потребителей Create: stress impact на единицу RPM,
умноженный на уровень. Крутить сеть выше возможности ядро не заставит: если сеть
перегружена, Create сам остановит вращение, и поле угаснет.

### Настройка на грани

Сделано так же, как у регулятора скорости вращения Create (проверено по исходникам):

- Настройки — поведения блок-сущности: `ScrollOptionBehaviour` для знака (притяжение /
  отталкивание) и `ScrollValueBehaviour` для уровня силы 1–4.
- Место на грани задаёт `ValueBoxTransform.Sided`: координаты «южной» точки (как
  `voxelSpace(8, 11, 15.5)` у регулятора) и условие, на каких гранях слот активен. Поворот
  под нужную сторону Create делает сам.
- Ввод: зажать правую кнопку мыши на слоте, откроется панель, провести по ней и отпустить —
  значение выбрано (в Create 6 вместо колёсика используется `ValueSettingsBoard`).
- Два слота на одной грани можно сделать через `ValueBoxTransform.Dual`, но у нас их
  две отдельные панели: на одной грани знак, на противоположной уровень силы.

Что нужно учесть: `ScrollOptionBehaviour` требует перечисление, реализующее
`INamedIconOptions`, а оно использует иконки Create (`AllIcons`). Своих иконок в Create
добавить нельзя, поэтому берём подходящие из готовых.

Модель ядра учитывает это: на одной боковой грани окно (видно вал), напротив него панель уровня силы, сбоку панель
знака, четвёртая грань глухая. Каждая настройка
имеет свой тип поведения: блок-сущность хранит поведения по типу, и два одинаковых заменяли бы друг друга.

### Редстоун

Сигнал на ядро выключает поле, как у остальных механизмов Create. Пока сигнал есть, ядро
крутится вхолостую, нагрузка с сети снимается, поле нет. Дальше можно рассмотреть
аналоговый сигнал как «диммер» силы, но в первую версию он не входит.

### Раскрутка и остановка

Поле не включается и не выключается мгновенно. Радиус и сила плавно догоняют целевое
значение (~1–2 секунды), иначе любое колебание скорости на валу дёргает всех внутри.
При остановке ядра игрок не падает «вдруг»: направление за те же секунды возвращается
к ванильному.

## Как считается гравитация

В каждой точке мира нужен вектор «вниз» и множитель силы.

Для каждого активного ядра *i* вклад в точке *p* (расстояние *d* до ядра):

```
a_i(p) = знак_i · g_i · fade(d / R_i) · направление_на_ядро

fade(x) = 1                        при x ≤ 0.6        плато вокруг тела
        = 1 − smoothstep(0.6,1,x)  при 0.6 < x < 1    плавный край
        = 0                        при x ≥ 1          снаружи поля нет
```

На плато сила постоянна, как на поверхности планеты. На краю она плавно уходит в ноль,
поэтому поле не имеет резкой границы.

### Выбор поля

Побеждает ядро с наибольшим |a_i(p)| в этой точке — «ядро, чьё притяжение здесь сильнее
остальных». В этом смысл *hill sphere*: для каждого ядра область, где оно побеждает.
(Предыдущая версия документа предлагала «побеждает самое слабое поле» — это было
ошибкой: так маленькое ядро было бы невозможно использовать рядом с большим.)

Чтобы направление не прыгало на границе, рядом с ней оба кандидата смешиваются:

```
r = |a_winner| / |a_runnerup|
вес_победителя = 0.5 + 0.5 · smoothstep(1.0, 1.25, r)     (r = 1 → 0.5, r ≥ 1.25 → 1)
направление = slerp(направление_второго, направление_победителя, вес_победителя)
```

Если векторы почти противоположны и величины равны (середина между двумя ядрами),
направление не определено. Тогда берётся среднее, а сила множится на ~0 — получается
«невесомость» между двумя телами, это нормальное поведение.

### Ванильный «низ»

Ванильный вектор вниз — это «фоновое поле» без ядра. Итоговое направление в точке:

```
итог = slerp(ванильный_низ, направление_ядра, fade_ядра)
```

Поэтому снаружи любого поля всё как в ваниле, а на краю поля переход плавный.

## Парение и вес конструкции (предложение, ждёт подтверждения)

Сейчас ядро **не** заставляет зависать в воздухе: оно подменяет направление «вниз». Притягивающее
ядро под вами делает так, что вы падаете на него и стоите на его «поверхности». Отталкивающее
ядро разворачивает «вниз» от себя. Парить в такой схеме нечем, поэтому для парения нужен
третий режим.

### Режим «невесомость» (третья настройка знака)

Знак ядра: притяжение / отталкивание / **невесомость**. В режиме невесомости направление
«вниз» не меняется, а ядро гасит силу тяжести внутри поля:

```
сила_после = сила_до · (1 − L · fade)        L — уровень силы режима: 0.25, 0.5, 1.0, 1.25
```

- `L = 1.0`: внутри плато гравитации нет совсем, предметы и игроки висят где остановились.
- `L = 1.25`: на плато небольшая подъёмная сила. Тело всплывает, пока поле не ослабнет до
  `fade = 1/L = 0.8` (примерно 0.72 радиуса), и там зависает на устойчивой высоте.
- Невесомость складывается с остальными ядрами: сначала считается обычное поле (планета или
  ваниль), потом множитель от ядер невесомости.

**Как двигаться в невесомости:** ходить нельзя, поэтому управление как при полёте в воде:
пробел — вверх, Shift — вниз, WASD — по взгляду, с инерцией (скорость не гасится мгновенно).
Урон от падения при `сила_после` около нуля не наносится. Это нужно реализовать отдельным
хуком движения.

### Как влияет вес конструкции

**Игроки, предметы, существа:** веса в ваниле нет, всё одинаково.

**Корабли Sable (по умолчанию):** поле — это ускорение, а сила = масса × ускорение. Значит
тяжёлый и лёгкий корабль падают, парят и садятся одинаково, вес ничего не меняет. Плюс:
предсказуемо и просто. Минус: маленькое ядро может подвесить огромную станцию.

**Режим «подъёмная сила» (вторая версия, по желанию):** ядро поднимает не ускорением, а силой,
пропорциональной взятой нагрузке: `грузоподъёмность = SU · k_lift`. Сумма масс конструкции в
поле сравнивается с ней: если масса больше, конструкция опускается, и чем тяжелее, тем
сильнее. Тогда вес важен, а «много ядер на тяжёлый корабль» становится инженерной задачей в
духе Create. Sable отдаёт массу тела: у серверного подуровня есть `getMassTracker()` (суммарная масса и центр масс). Силы в шаг физики кладутся как точечные через `QueuedForceGroup.applyAndRecordPointForce(точка, сила)`. В Sable уже есть группы сил `GRAVITY`, `LEVITATION` и `MAGNETIC_FORCE`, свою можно зарегистрировать рядом.

Рекомендация: в первой версии делать только ускорение (вес не влияет), режим грузоподъёмности
отложить.

### Известное свойство планетной схемы

Если ядро над игроком, на краю поля «вниз» плавно переворачивается через боковое направление,
потому что вектор «вниз» ванили и вектор к ядру противоположны. Это то же, что идти по
шару на другую сторону: там неизбежно проходишь через бок. Такое поведение тестируется
отдельно на игре.

### Что гравитация затрагивает

Первая версия: игроки, предметы и остальные существа. Ориентация модели поворачивается
вместе с «низом»; поворот камеры отдаётся Aeronautics Camera Sync, анимация плавная, не
щелчок.

Не в первой версии:

- **Жидкости**: поток воды в ванили зашит в направление «вниз». Менять его — отдельная
  большая задача; обещание «лить воду на планету» отложено до тех пор, пока не будет
  понятно, как это делать без поломки других модов.
- **Падающие блоки** (песок, гравий).
- **Снаряды и частицы**.

### Сервер и клиент

Сервер — источник истины: список активных ядер, их радиусы и знаки лежат на сервере.
Клиенту нужны те же данные для предсказания движения игрока и для очков, поэтому список
активных полей рядом с игроком рассылается дельтами при изменении (а не каждый тик).

Производительность: поля хранятся в пространственном индексе по сетке, запрос в точке
смотрит только соседние ячейки. Есть ограничение на число активных ядер на мир (конфиг,
по умолчанию 256). Ядро в незагруженном чанке неактивно (и вращение там тоже стоит).

## Очки

Предмет в слот головы. Показывают поля, пока надеты. Всё рисуется только на клиенте, на
сервер ничего лишнего не уходит.

Что видно:

- **Граница поля**: полупрозрачная оболочка на расстоянии R от ядра. Цвет по знаку:
  притяжение и отталкивание различаются цветом и формой стрелок. Плато (0.6·R) рисуется
  более плотной оболочкой, чем край.
- **Направление «низа»**: короткие стрелки/линии тока вокруг игрока, показывают вектор в
  каждой точке.
- **Границы холл-сфер**: там, где два поля перехватывают друг друга, линия раздела —
  видно, чьё поле побеждает где.
- **Подробности при взгляде на ядро**: RPM, потребляемые SU, радиус, уровень силы, знак,
  причина простоя («нет вращения», «редстоун», «перегрузка сети»).

Ограничения: рисуем только поля в пределах ~64 блоков, стрелки ограничены по количеству,
чтобы кадры не падали. Без очков поле невидимо — это сознательное решение, оно делает
очки нужным предметом, а не косметикой.

Совместимость с очками инженера из Create: Create показывает свою кинетическую
информацию, мы — свою; ядро по взгляду в обычные очки инженера ведёт себя как любой
кинетический блок.

## Ponder (в игре «Размышление»)

Так сделано у Create (по исходникам Create 6.0.11); для нас это план, ничего не написано.

- Ponder — отдельная библиотека (`net.createmod.ponder`, версия 1.0.85 для 1.21.1), Create
  тянет её через jar-in-jar. Мод подключает свой плагин: класс, реализующий `PonderPlugin`,
  с `getModId()`, `registerScenes`, `registerTags`, `registerSharedText`. Регистрируется
  на клиенте вызовом `PonderIndex.addPlugin(...)`.
- **Сцена** — метод `(SceneBuilder, SceneBuildingUtil)`. Сначала `title(id, "заголовок")`
  и `configureBasePlate`, потом по таймлайну: `world().showSection(...)`, `idle(тики)`,
  `overlay().showText(...)`, `showControls(...).rightClick()`, `world().setKineticSpeed(...)`,
  `effects().indicateSuccess(...)`, `markAsFinished()`.
- **Привязка сцены к блоку**: `helper.forComponents(блок).addStoryBoard("имя_сцены", метод, тег)`.
  Это добавляет сцену в окно Ponder блока, и она показывается по нажатию `W` на предмете.
- **Постройка сцены** — структура в `assets/<mod>/ponder/<имя_сцены>.nbt`. Это обычная
  схема (schematic), сохранённая в игре.
- **Текст**: фразы из кода (`title`, `text`) не руками переводятся, а выгружаются через
  datagen в lang (`create.ponder.<сцена>.header`, `.text_1`, ...), из которого потом делается
  перевод.
- **Теги** (`registerTags`) собирают сцены в страницы-списки («Источники вращения» и т.п.).
  Можно использовать общие теги Create, чтобы ядро показывалось в тех же списках.

Для ядра нужны три сцены: «запуск и радиус от скорости», «настройки: знак, уровень силы,
редстоун», «очки и видимость поля».

## Конфиг

Конфиг серверный (синхронизируется с клиентами, чтобы предсказание движения совпадало с
сервером). Сейчас в нём все числа поля: диапазон скоростей и радиусов, список уровней
притяжения и список уровней невесомости (число уровней задаётся длиной списка), нагрузка на
RPM, плато и ширина смешивания, время раскрутки, лимит ядер на мир. Если значения
противоречат друг другу (например, плато 1 или минимальный радиус больше максимального),
мод пишет предупреждение и берёт значения по умолчанию.

Ещё в конфиг (по мере появления механик): какие существа подвержены полю (игроки, мобы,
предметы, снаряды), отключение урона от падения в невесомости, включённые знаки ядра,
список измерений, где поля работают, дальность и количество стрелок у очков, множитель
силы для кораблей, видимость настроек.

## Прогрессия

1. Найти руду `gravite` **только в глубинном сланце**, глубоко под землёй.
2. **Обработка через механизмы Create**, простая плавка не работает:
   - руда (или `raw_gravite`) в **дробильных колёсах** даёт дроблёный гравит (иногда в двойном
     размере, из руды ещё и опыт);
   - дроблёный гравит в **вентиляторе над синим огнём** (огонь душ, процесс «призрачная обработка»)
     даёт призрачный гравит;
   - призрачный гравит в **миксере над сверхнагретой горелкой** (горелка с блейзовым тортом)
     даёт **расплавленный гравит** (250 мБ на один призрачный гравит);
   - расплавленный гравит **разливается носиком Create на изумруд**: изумруд и 250 мБ дают
     один слиток. Изумруд при этом расходуется.
3. Прессом Create из слитков сделать **гравитовые пластины** (`gravite_sheet`).
4. Из девяти пластин (3×3) скрафтить одну **плиту** (`hill_plate`).
5. **Ядро** (`hill_core`): 4 плиты по углам, 2 прецизионных механизма (сверху и снизу), 2 латунных
   корпуса (слева и справа), вал в центре. То есть нужны и наши плиты, и Create из середины игры
   (латунь, прецизионный механизм).
6. **Очки** (`hill_goggles`): 1 гравитовая пластина, 2 латунные пластины и 2 стеклянные панели.
7. Раскрутить ядро, настроить, смотреть очками. Затем корабли, гироскоп.

Состав рецептов временный и подбирается на игре; пока это крафт на верстаке. Усложнение через
последовательную сборку Create (нажать, влить, прессовать) — отдельная идея на потом.

## Совместимость и сборка

- Minecraft 1.21.1, Java 21, Gradle Kotlin DSL.
- Математика полей, выбор победителя и интерполяция — чистая Java в `common`, без
  Minecraft, поэтому покрывается юнит-тестами.
- Блок ядра и всё, что трогает Create, — в модуле `neoforge`.
- Обязательные зависимости: Create, Sable, Aeronautics Camera Sync. Мягких нет — не
  разводим режимы «с кораблями» и «без».
- Sable: сила отдаётся из сервера в шаг его физики как внешняя; клиент ничего не считает,
  иначе корабли разъедутся.
- Aeronautics Camera Sync отвечает за наклон камеры, свою реализацию наклона не пишем.
  Мод только сообщает ему вектор «низа» в точке камеры.

### Только NeoForge

Create 6.0 официально выходит только для NeoForge (1.21.1), а ядро — кинетический блок
Create, поэтому мод делается только под NeoForge, Create — обязательная зависимость.
Fabric из проекта убран. Модуль `common` остаётся: в нём математика полей без Minecraft,
которая покрывается юнит-тестами.

## Решения и открытые вопросы

Решено:

- Питание ядра — вращение Create (было вопрос №3).
- Только NeoForge, Create обязателен, Fabric убран.
- Радиус от скорости, сила от уровня и момента, знак и редстоун — как описано выше.
- Нет отдельного отталкивателя и грузила (их заменяют настройка ядра и очки).
- Выбор поля — по наибольшему вкладу со сглаживанием; прежняя идея «слабейшее побеждает»
  отменена.
- Тиров по названию нет: ядро одно, различие — настраиваемый уровень силы.
- Руда одна, редкая часть рецепта — детали Create.
- Названия: руда `gravite`, ядро `hill_core`.

Остаётся решить:

1. **Спавн руды** — руде нужен worldgen feature. Запрет «никакой генерации» относится к
   рельефу и измерениям. Руда не появится в уже сгенерированных чанках, поэтому «безопасно
   добавить в старый мир» верно только для блоков, не для руды. Если нужно, чтобы мод был
   играбелен в старом мире, надо давать руду и другим путём (например, крафтом из других
   материалов).
2. **Числа** — все формулы и константы выше нужно проверять на игре: в частности, k, R_max,
   значения g по уровням и сравнение с реальными SU источников Create.
3. **Ввод настроек** — точный механизм выбора грани и уровня определится по тому, что
   даёт API Create.

## Порядок работ

1. Математика полей (`common`, чистая Java + тесты): вклад ядра, fade, выбор победителя,
   сглаживание, ванильное смешивание.
2. Поворот игрока и камеры по вектору «низа» на тестовом блоке без Create (чтобы
   проверить самое рискованное — плавный переход на границе).
3. Блок ядра с вращением Create (NeoForge), настройки, редстоун, раскрутка.
4. Очки и их оверлей.
5. Руда, рецепты, плита.
6. Отдача сил в Sable.
